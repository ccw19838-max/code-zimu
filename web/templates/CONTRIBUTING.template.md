# 参与【项目名称】

> 建议规则 v0.1，待团队采纳。请由维护人填写本项目约定；文档中的流程不代表 GitHub 已配置保护分支、ruleset 或必需检查。

## 归属与权限

团队共同维护的仓库归属 `【组织名】`，成员使用自己的 GitHub 账号协作。团队新仓库默认私有；需要公开时，由负责人确认代码权利、第三方许可和敏感信息检查后，按团队流程决定。个人项目进入团队管理前，由所有者和团队明确转移或授权安排，避免把个人仓库默认视为团队共有。

建议组织 Base permissions 为 None，按 Team 对指定仓库授予 Read 或 Write；只为需要管理仓库的人提供管理权限。负责人为 `【@负责人】`，备用负责人为 `【@备用负责人】`。权限由组织管理员按已采纳的规则配置。

## 开始工作

1. 先查已有 Issue 和 PR，避免重复工作。功能或问题 Issue 写清背景、预期行为、复现方式、范围和验收条件；小修复可以在 PR 中完整说明。
2. 认领负责人并确认目标分支。涉及接口、数据迁移或较大范围变更，先与维护人确认方案。
3. 从项目约定的基线建立短期分支，例如 `feature/【简短名称】` 或 `fix/【简短名称】`。权限允许时使用组织仓库内分支；采用 fork 必须符合组织对私有仓库和代码存放的政策。

## 分支约定

| 用途 | 本项目实际分支 | 约定 |
| --- | --- | --- |
| 稳定版本 | `【通常为 main；填写实际名称】` | 保持可构建、可验证，变更通过 PR 合入 |
| 日常协作 | `【填写实际名称；现有 dev/cc 可继续使用】` | 集成已评审变更，达到发布条件后按项目流程进入稳定分支 |
| 临时开发 | `feature/【名称】`、`fix/【名称】` | 一项工作一个分支，合并后清理 |

沿用项目已有的 `main`、`dev/cc` 或其他明确约定，不为套用模板擅自改名、重置分支或变更默认分支。禁止直推或 force push 受保护分支；需要修改自己尚未合并的分支历史时，先确认无人依赖该历史。

## 提交与 PR

- 提交聚焦一项变化，说明做了什么和为什么。可采用 `feat(scope): 描述`、`fix(scope): 描述`、`docs(scope): 描述` 等格式；涉及 Issue 时写入编号。
- PR 写清问题、变更行为、实际验证结果、风险及回滚办法。界面变更附真实截图或演示，非界面变更给出可复现的输入输出或检查结果。
- 每个 PR 至少由一名非作者评审通过，再由有合并权限的成员处理；不要以作者自查替代同行评审。重大接口或数据变更需邀请相关模块负责人。
- 运行适合本次变更的检查，解决失败项。必需的项目命令：`【填写实际测试／构建／静态检查命令】`。未运行的检查必须写明原因及替代验证。
- 同步 README、配置样例和使用文档，使功能、场景、输入输出、结果展示、启动方式与代码一致。
- 不在公开 Issue、PR 或日志中粘贴凭据和敏感数据。紧急情况按维护人已确认的流程处理，记录原因、操作人与事后评审；紧急标签本身不授权绕过 GitHub 规则。

维护人需确认组织计划、仓库类型和权限是否支持相应 ruleset、保护分支、必需检查与代码所有者审批，再配置并验证。仅有这份文档或 CODEOWNERS 文件不会强制上述流程。

## 凭据、依赖与许可

- 不提交 token、密码、私钥、生产配置或敏感原始数据。提交前检查差异，配置样例只保留字段名和安全占位值。
- 发现凭据已进入仓库时，立即通知维护人并撤销或轮换凭据，再协调历史清理和影响检查；只删除当前文件不能消除泄露。
- 新增依赖说明用途和来源；引入第三方代码、字体、图片、数据前核对许可证、署名和分发条件，更新相关清单。
- 未经权利人确认，不擅自修改项目许可证或将私有代码公开。

## 发布、移交与归档

发布由 `【发布负责人／Team】` 按项目的 Release 检查表执行，记录提交、版本、验证和回滚方式。成员退组或停止维护前，应把未完成工作、仓库权限、部署配置、发布能力、文档和数据恢复步骤移交给负责人及备用负责人；个人凭据应撤销或由接任者使用自己的身份重新授权。

归档前确认最后可用版本、未解决问题、替代方案和备份恢复记录。备份不等于可以恢复，应按项目约定实际演练恢复。
